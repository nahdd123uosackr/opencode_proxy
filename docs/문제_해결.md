## P0 (치명적): 풀 hold-back이 chat-format 스트림을 content로 인식 못 함

### 증상

- 풀(:8770) 경유 스트리밍이 전 멸: `{"error":"empty stream from upstream"}` 또는 `{"error":"This operation was aborted"}`
- OmniRoute 콤보 스트리밍은 keepalive ping만 수십 개 흐르고 content 0개로 종료

### 재현 (각 3회 이상)

```bash
# 업스트림(로컬 8769) 직접 스트리밍 → 정상 (content 있음)
curl -sN http://192.168.200.2:8769/v1/chat/completions -d '{"model":"opencode/muse-spark-1.2-contributor-free","messages":[...],"max_tokens":300,"stream":true}'
# → data: {"...":"chat.completion.chunk","choices":[{"delta":{"content":"1\n"}}]} ... [DONE]   (247 bytes, 2회 동일 결과)

# 풀 경유 동일 요청 ×4 → 전부 실패
# → {"error":"empty stream from upstream"}
# 로그: [empty-stream] vercel-opencode-proxy-two bytes=247 (3.3s) ← 정상 스트림(247B)을 받고도 오판

# nemotron(non-muse)도 동일하게 깨짐 → muse 전용 문제가 아님
```

### 원인 (`/opt/opencode-pool/pool.js` hold-back, 407~408행 부근)

```js
const isContent = frame.includes('output_text.delta')
               || frame.includes('response.function_call_arguments.delta');
if (isContent || bufferedBytes > MAXBUF) { started = true; flushBuffered(); }
```

- 콘텐츠 감지 패턴이 **OpenAI Responses API 이벤트명만** 지원함.
- 그런데 서버리스 업스트림(Vercel/Deno/로컬 index.js)은 muse를 Responses로 변환한 뒤 **다시 chat chunk(`"delta":{"content":"..."}`)로 역변환**해서 스트리밍함 (09문서 "muse 변환 레이어").
- 결국 모든 프레임이 `isContent=false` → 끝까지 버퍼링 → 스트림 종료 시 `!started` → **정상 스트림을 empty-stream으로 오판**.

검증 시뮬레이션(실제 정상 스트림 파일 대입): `프레임 3개 중 분류기 인식 0개`.

### 연쇄 피해 (이것이 "실패가 많다"의 본체)

1. 오판 때마다 `markFail(u)` → **정상인 업스트림 15개가 줄줄이 cooldown** (실측: fails 최대 16, cooldown 1800s, ready=0/15). 자해적(self-inflicted) 서비스 중단.
2. muse 헬스 점수 오염: score 0.14(ok43/fail265), nemotron-ultra 0.01 — 동티어 폴백 선택 왜곡.
3. 풀이 40초(REQUEST_DEADLINE_MS)까지 헛돈 뒤 실패 → 9router lockout("(reset after Ns)") → OmniRoute 큐 60초 초과 → **504 폭증** (muse 504 avg 60,277ms).
4. 일부 경로에선 풀 실패 후에도 OmniRoute가 keepalive+[DONE]만 달랑 끝내는 **빈 성공 스트림** 반환 (아래 P1-2).

### 해결책 (pool.js 패치안)

프레임 JSON 파싱 기반으로 양 형식 모두 인식 + 빈 content 제외:

```js
const frameIsContent = (frame) => {
  if (frame.includes('output_text.delta') || frame.includes('response.function_call_arguments.delta')) return true;
  for (const line of frame.split('\n')) {
    if (!line.startsWith('data:') || line.includes('[DONE]') || line.includes('keepalive')) continue;
    try {
      const j = JSON.parse(line.slice(5).trim());
      const d = j.choices?.[0]?.delta;
      if (!d) continue;
      if (typeof d.content === 'string' && d.content.length > 0) return true;      // chat chunk
      if (Array.isArray(d.tool_calls) && d.tool_calls.length) return true;          // tool args
    } catch (_) {}
  }
  return false;
};
// 기존 isContent 자리에 frameIsContent(frame) 사용, sdeltas/hasTool 계산에도 재사용
```

추가 권장:
- empty-stream 시 `markFail`을 즉시 적용하지 말고(오진 시 업스트림 오염) 최소 1회 재확인 또는 cooldown 상한을 60~120s로 축소.
- 배포 후 검증 시나리오에 **"반드시 스트리밍 회귀 테스트"** 추가 (이번 사례는 비스트리밍 검증만으로 배포됨).
- 패치 후 `/tmp/lp_sse_*.txt` 같은 실제 캡처로 회귀 확인.

## P1: OmniRoute resilience와 체인 타임아웃 미스매치

### P1-1. 큐 만료 504 (76건)

- 에러: `Request exceeded OmniRoute's local rate-limit execution expiration (legacy resilienceSettings.requestQueue.maxWaitMs=60000ms)`
- 풀의 REQUEST_DEADLINE_MS=40s + 9router retry/lockout + 콤보 maxRetries=1이 겹치면 60s를 넘기기 쉬움. muse reasoning 자체가 2~10s인 점도 가중.
- **해결**: 콤보/전역 maxWaitMs를 90~120s로 상향하거나, 풀 REQUEST_DEADLINE_MS를 20~25s로 낮춰 체인 총량 < 60s 보장. (권장: 후자 — 클라이언트 타임아웃이 더 짧으면 무의미)
- 참고: `server.env`의 `STREAM_RECOVERY_ENABLED=false`는 이미 반영돼 있었음(이전 문서의 "미반영" 해소).

### P1-2. 실패를 "빈 성공 스트림"으로 반환 (재현 3회)

- 풀 전체 실패 시에도 OmniRoute가 HTTP 200 SSE로 keepalive 24개 + `[DONE]` + content 0개를 전달 (13:41 실측 /tmp/sse_*.txt). 클라이언트 입장에선 "성공했는데 답 없음".
- **해결**: 업스트림 실패 확정 시점에는 반드시 에러 이벤트(`data: {"error":...}`) 또는 5xx로 종료. OmniRoute SSE 품질검사("non-ping event 없음")는 이 때문에 발화하는 측면이 있음.

## P2: 동적 티어(v5) 카탈로그에 미검증/불가 모델 포함

- `models.dev/api.json`에서 자동 편입된 모델 중 zen이 실제 거부하는 것이 있음: `opencode/longcat-2.0-free` → `ModelError: Model longcat-2.0-free is not supported`(HTTP 200 랩) — 12:39 401로 관측, health fail=6.

- **해결**: 카탈로그 반영 시 신규 모델은 1회 실호출 검증(canary) 통과 후 ALT 후보군에 편입. `ModelError|not supported` 응답은 해당 **모델**을 DYN.byModel에서 영구 제거(업스트림 cooldown과 분리 — 현재는 200 랩 에러라 업스트림만 깎이는 왜곡 가능).

## P5: 9router 비스트리밍 응답이 SSE로 래핑됨 (잠재 호환성 위험)

- :20130에 `stream` 미지정 요청 → **`content-type: text/event-stream`** + 바디 `{완전한 chat.completion JSON}data: [DONE]\n\n` (3회 재현, od로 확인).
- OmniRoute는 파싱에 성공(200 기록)하지만, strict OpenAI SDK로 :20130을 직접 쓰는 클라이언트는 JSON 파스 실패 위험. 과거 `[MALFORMED-200] empty_choices` 계열 장애와 동종.
- **해결**: 9router에 force-stream 언래핑이 필요하면 cline shim과 같은 방식(stream:true 강제 호출 후 비스트리밍 조립) 적용. 현재 체인(OmniRoute 경유)만 쓰면 치명적이지 않음.

# P7: Vercel 스트림 120초 절단 — Edge가 아니라 자체 AbortSignal (2026-08-26 해결)

## 질문

"Vercel edge function을 이용하면 스트림 응답이 끊길 수 있다" — edge function인지, 선택 가능한지, 실제로 긴 응답이 끊기는지 확인.

## 답변 요약

1. **Edge function 사용 중이 아니다**: 현재 배포는 Node.js 런타임 lambda(`lambdaRuntimeStats: {nodejs:2}`, 리전 iad1).
2. **선택은 가능하지만 권장하지 않음**: `export const runtime='edge'`로 전환 가능하나, Vercel이 신규 프로젝트에서 deprecated. Edge 제약: 25초 내 첫 응답 시작 필수, 스트리밍 최대 300s.
3. **실제 끊김이 관측됐다 — 단, 원인은 Edge/Vercel이 아니라 우리 코드**: kilo 분기의 `AbortSignal.timeout(120000)`이 정상 장문 스트림을 **정확히 120초에 절단**(2회 재현: 120.3s).

## 실측 데이터

| 테스트 | 결과 |
|---|---|
| kilo 게이트웨이 직접(Vercel 우회) 장문 스트림 | ✓ 178s 완주, [DONE] 정상 — 업스트림 무결립 |
| jet 장문 스트림(수정 전) ×2 | ✗ 각각 120.3s/121s에 JSON 청크 한가운데 하드 컷, [DONE] 없음 |
| jet 재측정(수정 후) | ✓ 120s 통과 → **301s**에 종료 = 플랫폼 한도 도달 |
| 수정 후 짧은 응답 회귀 | ✓ muse 비스트리밍 200 / ox-alpha 스트리밍 content 32프레임 |

## 플랫폼 한도 (Vercel 공식 문서, fluid compute 기준)

- 계정 플랜: **Hobby** → 함수 maxDuration 기본/최대 **300s** (연장 불가)
- Pro: 최대 800s (`vercel.json`의 `functions.maxDuration` 설정), 베타로 1800s
- Edge 런타임: 첫 응답 25s + 스트리밍 300s (deprecated)

## 수정 내용

- `/root/vercel-opencode-proxy/api/index.js` + 로컬 2대 `/opt/opencode-proxy/api/index.js`: kilo 분기 `AbortSignal.timeout(120000)` → `KILO_STREAM_TIMEOUT_MS` env(기본 300000). Deno는 해당 타임아웃이 원래 없어 변경 불필요.
- Vercel 9개 재배포 완료.

## 결론 및 남은 제약

- **5분 미만 스트림**: 모든 Vercel 업스트림에서 완전히 안전해짐.
- **5분 초과 스트림**: Hobby 플랫폼 상한으로 절단됨 — 구조적 한계. 대응 옵션: ① Pro 업그레이드 + `maxDuration: 800` 설정, ② 장기 응답이 많은 워크로드는 로컬/Deno 업스트림(Deno는 타임아웃·플랫폼 컷 없음) 우선 라우팅.
- 참고: 절단 시 클라이언트는 HTTP 200 + 잘린 SSE를 받으므로(함수 강제 종료), 클라이언트 측 finish_reason 유무 검사 권장.

# P6: TEST 콤보 400 에러 — serverless 배포판 코드 불일치 (2026-08-26 해결)

## 증상

TEST 콤보에서 oepn-proxy(=instance2:8770 풀, api_type=responses) 경유 멤버들이 실패:
- `kilo/thinkingmachines/inkling:free` ×2 → `[400] Input required: specify "prompt" or "messages"`
- `opencode/x-preview-f-free` → `[400] [1214] Input cannot be empty`

- `(Console)`은 provider 이름이 아니라 **opencode-proxy 자신의 에러 래핑 문구**(bifrost의 `config_providers`에 그런 이름 없음 — bifrost logs.db 조회로 provider가 실제로는 `opencode-zen1`임을 확인).
- 03/06 문서의 "완벽 검증"은 전부 단발성 요청(`say hi`, `calculator 15*3`)이었어서 **과거 tool_call이 포함된 멀티턴 히스토리**를 재전송하는 경로가 한 번도 커버되지 않았고, 장기 실행 중인 Hermes 세션(461개 메시지, 실제 tool_calls 다수 포함)에서 처음 노출됨.

## 원인 (`/opt/opencode-proxy/api/index.js`, oracle2 한정)

`museToInput()`의 `assistant`/`tool` 분기가 Responses API 스펙을 두 가지로 위반:

1. **`function_call`을 `content` 배열 안에 중첩** — 스펙상 `function_call`은 `input` 배열의 **최상위(top-level) 아이템**이어야 하는데, `{role:'assistant', content:[{type:'function_call',...}]}` 형태로 content-part인 것처럼 잘못 합쳐 넣고 있었음. `function_call`은 `content` 파트 타입 유니온(`input_text`/`output_text`/`input_image`/`refusal` 등)에 없는 타입이라 스키마 불일치.
2. **`function_call_output`도 동일하게 `role:'user'` 메시지의 `content` 안에 중첩** — 이것도 top-level 아이템이어야 함.
3. **assistant 텍스트 파트의 타입이 `"text"`** — Responses API의 어시스턴트/출력 측 content-part는 `output_text`(또는 `refusal`)만 허용하고 `"text"`는 지원 타입에 없음. (`input[3]`이 정확히 이 케이스로 재현됨: 과거 `assistant` 메시지의 평문 응답이 `{type:'text',...}`로 직렬화되어 있었음.)

세 버그 모두 "히스토리에 과거 tool_call 왕복이 있어야만" 드러나는 조건이라 03/06 문서의 단발성 검증에서 놓쳤음. 참고로 같은 저장소의 **oracle1 로컬 사본, `/root/vercel-opencode-proxy/api/index.js`, `/root/deno-opencode-proxy/main.ts`는 이미 올바른 구현**(`output_text` + top-level `function_call`/`function_call_output`)이었음 — oracle2의 `/opt/opencode-proxy`만 단독으로 구버전 로직으로 드리프트된 상태였음(P6 문서가 경고한 "서버리스 소스 동기화 누락"의 변주 — 이번엔 반대로 **로컬(oracle2) 쪽이 구버전**).

# P10: 504 "Direct response did not start within 30000ms" — pool.js hold-back의 무기한 무음 구간 (2026-09-10 해결)

## 증상

- OmniRoute(bifrost) → `opencode-proxy`(pool, 8770 경유) → `muse-spark-1.3-contributor-free`, 큰 컨텍스트(53,198 토큰 압축) 요청에서 60.4초 만에:
  ```
  [504]: Direct response did not start within 30000ms — retrying on a fresh socket
  ```
- P9와 달리 에러 타입이 bifrost 자체의 클라이언트 타임아웃 문구(우리 코드/zen의 에러 포맷이 아님) — bifrost logs로 봐도 `service_overloaded`류의 zen 에러가 아니라, **응답이 아예 시작되지 않아서** bifrost의 HTTP 클라이언트가 스스로 포기하고 재시도한 것.

## 원인 (`/opt/opencode-pool/pool.js`, hold-back 스트리밍 처리)

P0(문제_해결.md 상단)에서 도입한 hold-back 로직은 **첫 content 프레임이 올 때까지 클라이언트에 어떤 바이트도(HTTP 상태줄/헤더조차) 보내지 않고 전부 메모리에 버퍼링**하도록 설계돼 있었다(`res.writeHead`가 `flushBuffered()` 안에만 있고, 이 함수는 `frameHasContent()`가 참이거나 8MB를 넘겨야 호출됨). 이건 "빈 스트림을 성공으로 오판하지 않기 위한" P0의 의도된 설계였지만, 부작용으로 **업스트림이 정상적으로 살아서 일하고 있어도, 첫 실제 콘텐츠가 나오기까지 오래 걸리면(큰 컨텍스트일수록 muse-spark의 reasoning 단계가 길어짐) 클라이언트 쪽 소켓은 완전한 무음 상태**가 됨. bifrost의 HTTP 클라이언트는 "30초 동안 응답이 전혀 시작 안 되면 죽은 걸로 간주하고 재시도"하는 자체 타임아웃이 있어서, 이 무음 구간이 30초를 넘기면 (풀은 멀쩡히 일하고 있었는데도) 연결이 끊기고 재시도 → 그마저도 다시 무음에 걸리면 60초 뒤 최종 504로 사용자에게 전달됨.

## 진단/재현

- 헤더가 언제 나가는지는 `curl -w '%{time_starttransfer}'`로는 부정확함(body 바이트 기준) — **raw TCP 소켓으로 recv() 타임스탬프를 직접 찍어야** 헤더 전송 시점을 정확히 확인 가능.
- 가짜 slow 업스트림으로 격리 재현: `res.writeHead()` 직후 반드시 `res.flushHeaders()`를 명시적으로 호출해야 함 — 안 그러면 Node가 헤더를 body 첫 write와 묶어서 보내버려서, "헤더는 빨리 오고 body만 늦게 온다"는 실제 상황을 재현할 수 없음(이 실수로 첫 검증 시도가 잘못된 결론을 낼 뻔했음).
- `POOL_UPSTREAMS`를 가짜 서버 하나로 임시 override(`systemd` drop-in) → 검증 후 원복.

## 수정

`pool.js`의 hold-back 읽기 루프에 **시간 기반 안전장치**를 추가: `HOLDBACK_TIMEOUT_MS`(기본 15000ms, env로 조정 가능) 동안 content가 없으면 버퍼링된 내용(없으면 빈 바디)이라도 강제로 헤더+버퍼를 flush해서 클라이언트에게 "연결이 살아있다"는 신호를 준다. 이후 프레임은 기존 패스스루 경로(`else res.write(frame)`)로 그대로 흘러감. `reader.read()`는 WHATWG 스트림 제약상 동시에 하나만 걸 수 있어서, `pendingRead`를 루프 밖에서 유지하며 1초 간격 `tick` 타이머와 `Promise.race`로 경합시키는 방식으로 구현(매 요청마다 새 `read()`를 걸지 않고 이미 걸린 것을 재사용).

```js
const HOLDBACK_TIMEOUT_MS = parseInt(process.env.HOLDBACK_TIMEOUT_MS || '15000', 10);
const holdStart = Date.now();
let pendingRead = reader.read();
while (true) {
  const tick = new Promise(resolve => setTimeout(() => resolve('__HOLDBACK_TICK__'), 1000));
  const result = await Promise.race([pendingRead, tick]);
  if (result === '__HOLDBACK_TICK__') {
    if (!started && (Date.now() - holdStart) > HOLDBACK_TIMEOUT_MS) { started = true; flushBuffered(); }
    continue;
  }
  const { done, value } = result;
  pendingRead = done ? null : reader.read();
  if (done) break;
  // ...기존 프레임 처리...
}
```

15000ms는 bifrost의 ~30000ms 무음 한도와 pool 자체 `REQUEST_DEADLINE_MS`(25000ms)보다 충분히 여유 있게 짧게 잡은 값.

## 검증

| 항목 | 결과 |
|---|---|
| 가짜 업스트림(헤더 즉시, content 25초 후) — raw socket 프로브 | 헤더 **15.01초**에 수신(강제 flush 확인), content는 25.09초에 정상 수신 |
| tick 로그 | 1초 간격으로 정확히 15004ms에 `[holdback-timeout]` 트리거 확인 |
| 실제 프로덕션 업스트림 40개로 원복 후 muse-spark 스트리밍 ×3 | ✓ 200 (4.6s/20.6s/34.7s — 정상 범위 지연, 강제 flush 미발동) |
| non-muse 회귀 | ✓ 200 (1.5s) |

## 교훈

- **`curl -w`의 `time_starttransfer`는 body 바이트 기준이라 "헤더가 언제 나갔는가"를 검증하는 데는 부적합.** 헤더 전송 타이밍을 정확히 보려면 raw socket에서 recv() 시점을 직접 찍어야 함.
- **테스트용 가짜 서버를 만들 때 `res.flushHeaders()`를 빼먹으면 Node가 헤더를 body와 묶어 보내서, 검증하려는 "헤더는 빠르고 body만 느림" 시나리오 자체가 재현이 안 된다** — 이번에 실제로 이 실수 때문에 첫 시도에서 "고치기 전이나 후나 20초에 다 온다"는 잘못된 관찰을 할 뻔했음.
- **"빈 스트림 오판 방지"(P0)와 "클라이언트 dead-air 타임아웃 방지"는 서로 다른 축의 문제이고, 하나를 고치다 다른 하나를 만들 수 있다.** hold-back은 P0를 고쳤지만 그 설계 자체가 이번 P10 버그의 원인이 됐음 — 무기한 버퍼링에는 항상 시간 상한을 같이 둘 것.

# P11: "muse-spark 성공 후 다음 모델로 넘어감" — 동티어 ALT 대체 + 리질리언스 스킵의 실체 (2026-09-10 조사·조치)

## 증상

사용자 관찰: omniroute 로그에서 muse-spark가 "성공"으로 찍히는데도 콤보가 다음 모델을 시도하는 것처럼 보임. 실시간 로그 상관관계 분석(`session_key`/콤보 분모 M 매칭)으로 원인을 두 갈래로 분리.

## 원인 A: omniroute 자체 리질리언스가 pool 경유 커넥션을 통째로 스킵

```
"all 1 active accounts cooling down for model opencode-proxy/opencode/muse-spark..."
Skipping .../opencode-proxy/... — model locked by resilience (cooldown active)
Trying model 2/48: .../opencode-zen1/opencode/muse-spark-1.3-contributor-free  ← 같은 muse-spark, 직결 경로
```

combo의 model 1(`opencode-proxy`, pool 8770 경유)과 model 2(`opencode-zen1`, oracle2:8769 직결)는 **둘 다 muse-spark**, 경로만 다름. omniroute 자체 계정 쿨다운(인메모리, SQLite `domain_circuit_breakers`엔 없음 — 별도 추적)이 걸리면 model 1은 시도조차 안 하고 model 2로 직행 — "성공했는데 다음으로 넘어간다"는 인상의 정체.

## 원인 B: pool.js의 동티어 대체(ALT)가 조용히 다른 모델로 성공 처리

`/opt/opencode-pool/pool.log`(사용자가 추가한 bifrost `opencode-proxy` 전용 로그) 실측:

```
[debug] 요청 model="opencode/muse-spark-1.3-contributor-free"
[ok] -> vercel-opencode-proxy-two ALT=opencode/nemotron-3-ultra-free (stream, deltas=2)
```

동시에 bifrost 쪽 `logs.db`엔 `model: "opencode/muse-spark-1.3-contributor-free", status: "success"`로만 기록됨 — **실제로 nemotron이 답했는데 muse-spark가 성공한 것으로 로그에 남음.** pool.js의 `buildAttemptPlan()`이 원래 "1) 원모델 1회 → 2) 실패 시 곧장 동티어 대체 모델로 전환" 순서였던 게 원인.

## 조치 1: 원모델 우선 재시도로 순서 변경 (`buildAttemptPlan`)

실패 시 곧장 ALT로 가지 않고, **원모델로 서로 다른 노드를 최대 5회(`SAME_MODEL_RETRY_LIMIT`, env로 조절)** 먼저 시도하도록 순서 변경. 그래도 다 실패해야 ALT로 감. 격리 테스트로 1~5번=원모델/다른노드, 6번부터 ALT 순서 확정 검증.

## 조치 2: Kilo Gateway 모델 전용 티어 분리

`refreshCatalog()`가 `models.dev`의 **opencode 네임스페이스만** 긁어오기 때문에, `kilo/*` 모델(오라클2 `/opt/opencode-proxy`가 별도로 브릿지하는 Kilo Gateway 모델)은 `DYN.byModel`에 전혀 안 잡혔음. 그 결과:
- 21개 중 9개는 티어 `null` → ALT 후보 자체가 없음
- 12개는 이름이 우연히 zen용 정규식(`FALLBACK_TIER_RE`)에 걸려 **서로 무관한 두 브랜드(zen ↔ kilo)가 동티어로 오매칭**됨 (예: `kilo/nvidia/nemotron-3-ultra-550b-a55b:free` → `/nemotron-3-ultra/i`에 우연히 매칭)

Kilo Gateway 자체 API(`api.kilo.ai/api/gateway/models`)가 `context_length`/`isFree`를 제공하는 걸 확인하고, `refreshKiloCatalog()`를 신설해 **zen과 완전히 분리된 네임스페이스**(`DYN.kiloByModel`, `KILO_FALLBACK_TIER_RE`, `KILO_MODEL_CATALOG`)로 10분마다 갱신. `tierOf()`/`alternateModel()`은 `kilo/` 접두사면 kilo 전용 테이블만 보도록 분기 — 네임스페이스 교차 매칭을 원천 차단.

검증: 재시작 후 `[kilo-catalog] tiers=XL:5,L:11,M:2,S:1 models=19` 정상 적재, `kilo/nvidia/nemotron-3-ultra-550b-a55b:free`가 실제 context_length(1M) 기반 XL 판정으로 바뀌고 ALT 후보도 kilo 안에서만 선택됨 확인.

## 조치 3: `UPSTREAM_TIMEOUT_MS` == `REQUEST_DEADLINE_MS` 설정 오류 수정

`timeouts.conf`가 둘 다 **35000ms로 동일**하게 설정돼 있었음 — 개별 시도 하나가 거의 전체 예산을 다 쓸 수 있어서, vercel 함수가 느리게(20~40초) 500을 낼 때 전체 요청이 44.9초까지 끌리다 bifrost(30초 한도)보다 늦게 응답해버림.

코드 확인: `UPSTREAM_TIMEOUT_MS`는 `fetch()`가 **응답 헤더를 받을 때까지만** 재고(`finally`에서 `clearTimeout`), 이미 시작된 본문 스트리밍(=muse-spark reasoning 시간)에는 관여 안 함 — 따라서 이 값을 줄여도 muse-spark의 정상적인 긴 사고 시간은 안 다침. `UPSTREAM_TIMEOUT_MS=8000` / `REQUEST_DEADLINE_MS=27000`으로 분리. 실측: "This operation was aborted"가 정확히 8.00x초마다 찍히며 개별 시도가 더 이상 20~40초씩 안 끔.

## 조치 4: hold-back 타임아웃을 "전체 요청 기준 남은 예산"에 맞춰 동적으로

조치 3 이후에도 실측에서 "8초 실패 + 22초 성공 스트림 = 총 30.2초"로 bifrost 한도에 거의 걸리는 케이스 발견 — hold-back의 15초가 **이번 시도 시작 시점** 기준으로만 계산돼서, 앞선 실패가 이미 써버린 시간을 전혀 반영 안 했기 때문.

```js
const CLIENT_PATIENCE_MS = 26000; // bifrost ~30초 한도보다 여유
const remainingBudget = CLIENT_PATIENCE_MS - (holdStart - reqStart);
const HOLDBACK_TIMEOUT_MS = Math.max(1000, Math.min(15000, remainingBudget));
```

`reqStart`(전체 요청 시작)가 hold-back 코드와 같은 스코프에 있어서 그대로 활용. 앞선 시도가 시간을 많이 썼을수록 이번 시도의 hold-back 유예가 자동으로 줄어들어, 누적 경과시간이 `CLIENT_PATIENCE_MS`를 구조적으로 못 넘게 됨.

## 최종 회귀 (조치 1~4 전부 적용 후)

| 테스트 | 결과 |
|---|---|
| muse-spark 스트리밍 ×3 (일부 2회 재시도 포함) | ✓ 3.1s / 3.8s / 20.1s (재시도 있었던 건도 26s 예산 안에서 안전하게 완료) |
| kilo 모델 직접 호출 | ✓ 200 |
| non-muse(nemotron 등) 개별 모델 변동성 | zen 쪽 자체 변동(노드 풀의 8%가 상시 쿨다운, 특정 모델이 간헐적으로 느림)은 클라이언트 타임아웃 튜닝만으로는 완전히 못 없앰 — 단, 실패해도 이제 27초 안에 깔끔하게 끝나고 40초씩 안 끔 |

## 교훈

- **"성공"이라고 로그에 찍힌 모델명을 그대로 믿지 말 것.** pool의 ALT 대체는 client-facing 로그에 반영이 안 돼서, 실제 응답 생성 모델과 요청 모델이 다를 수 있다.
- **동티어 판정에 쓰는 정규식 폴백은 그 모델 패밀리를 염두에 두고 만든 것이지, 문자열이 우연히 겹치는 다른 브랜드까지 커버하지 않는다.** 새 provider(Kilo 등)를 기존 프록시에 얹을 때는 티어링도 같이 점검할 것 — 안 그러면 서로 무관한 두 서비스가 "동티어"로 섞인다.
- **개별 시도 타임아웃과 전체 요청 데드라인은 항상 유의미한 간격을 둬야 한다.** 둘이 같으면 데드라인 체크가 사실상 무력화된다.
- **fetch()의 AbortController 타임아웃이 정확히 무엇을 재는지(헤더 vs 본문 전체) 확인 후 줄여야 안전하다** — 헤더 대기만 재는 타이머라면 줄여도 정상적으로 느린 스트리밍 성공 케이스를 안 다친다.
- **시간 기반 안전장치(hold-back 등)는 "이번 단계 시작 시점"이 아니라 "전체 요청 시작 시점" 기준 잔여 예산으로 계산해야, 여러 단계에 걸쳐 누적되는 지연이 클라이언트 한도를 넘기지 않는다.**

# P12: Kiro `profileArn is required for this request` (400) — 브랜드 게이트웨이가 profileArn 없는 계정을 거부 (2026-09-10 해결, 업스트림 PR)

## 증상

Kiro 계정 16개 중 Builder ID(=조직 프로필이 원래 없는) 계정 5개가 다음 오류로 실패:

```
[400]: profileArn is required for this request.
```

## 조사 — "이 계정이 망가진 건가" 검증

1. `omniroute`의 `storage.sqlite`에서 16개 Kiro 계정 전수 조회 → 5개가 `authMethod: builder-id`, `profileArn: null`로 동일 시그니처(같은 6분 이내 일괄 등록)
2. 로컬 `kiro-cli`(공식 클라이언트)로 실제 Builder ID 계정 로그인 상태 확인 → `whoami`가 "Logged in with Builder ID"라고 답함, `profile` 명령은 "IAM Identity Center 또는 External IdP 전용"이라며 명시적으로 거부 — **Builder ID는 애초에 profileArn이 없는 게 정상**
3. 그 kiro-cli 계정으로 실제 채팅(`claude-sonnet-4.5` 포함) → **정상 작동**. 즉 계정 자체는 멀쩡함.

## 근본 원인 — 브랜드 게이트웨이 vs CodeWhisperer 원본 호스트의 차이

같은 토큰·같은 요청을 두 호스트에 직접 비교:

```
POST https://runtime.us-east-1.kiro.dev/generateAssistantResponse
  -> 400 {"message":"profileArn is required for this request.","reason":null}

POST https://codewhisperer.us-east-1.amazonaws.com/generateAssistantResponse
  -> 200, 정상 스트리밍
```

`open-sse/executors/kiro.ts`의 `KiroExecutor.execute()`는 `authMethod`가 `api_key`/`idc`/external-idp가 **아닌** 모든 경우(Builder ID 포함) `runtime.*.kiro.dev` 브랜드 게이트웨이를 먼저 시도한다. 이 게이트웨이는 profileArn 없는 계정을 거부하지만, 원본 CodeWhisperer 호스트는 문제없이 처리한다.

그런데 폴백 대상 상태코드(`KIRO_ENDPOINT_FALLBACK_STATUSES`)는 `401/403/404`만 포함하고 **400은 의도적으로 제외**돼 있다(일반적으로 400=요청 본문 자체가 잘못된 거라 다른 호스트로 재전송해도 못 고침, 이라는 올바른 설계). 하지만 이 특정 400은 "요청 본문 문제"가 아니라 "이 호스트가 이 인증방식을 못 받아준다"는 **엔드포인트 능력 불일치**라서, 재전송하면 실제로 고쳐지는데도 그냥 에러가 사용자에게 그대로 나갔다.

## 수정

정확히 이 메시지(`"profileArn is required for this request"`)일 때만 좁게 폴백을 허용하는 헬퍼 추가 (400 전체를 폴백 대상으로 넓히지 않음 — 원래 제외 취지는 그대로 보존):

```ts
async function isBrandedGatewayProfileArnRejection(response: Response): Promise<boolean> {
  if (response.status !== 400) return false;
  try {
    const text = await response.clone().text();
    return text.includes("profileArn is required for this request");
  } catch {
    return false;
  }
}
```

`KIRO_ENDPOINT_FALLBACK_STATUSES.has(status) || await isBrandedGatewayProfileArnRejection(response)`로 OR 처리.

- 이슈: [diegosouzapw/OmniRoute#13192](https://github.com/diegosouzapw/OmniRoute/issues/13192)
- PR(draft): [diegosouzapw/OmniRoute#13193](https://github.com/diegosouzapw/OmniRoute/pull/13193) — 테스트 4개(정상 폴백 / 무관한 400은 폴백 안 함 / 기존 401·403·404 회귀 / api_key·idc는 애초에 브랜드 게이트웨이 안 탐)

## 교훈

- **"이 계정이 문제다"라고 단정하기 전에 공식 클라이언트로 직접 검증할 것.** 5개 계정 전부 강제로 profileArn을 우겨넣는(DB 직접 수정) 잘못된 해결책으로 갈 뻔했으나, kiro-cli 검증 덕에 진짜 원인(코드 버그)을 찾았다.
- **같은 계정·토큰이라도 어느 호스트로 가느냐에 따라 결과가 다를 수 있다.** "폴백 상태코드 400 제외"라는 설계 원칙 자체는 옳지만, 그 예외가 가려버리는 진짜 예외 케이스가 있는지는 실제 재현으로 확인해야 한다.

# P13: muse-spark 전역 블랙리스트 오탐 — response_format 거부가 모델 전체를 영구 차단 (2026-09-10 해결)

## 증상

코덱스(Codex CLI)로 `omni1` 콤보 호출 시 대화가 아예 진행 안 됨:

```
[502]: provider API error: {"error":"empty stream from upstream"}
프로토콜: OpenAI-Responses, /v1/responses, 지속시간 13.1s
```

## 조사

- bifrost `logs.db`에서 이 요청을 직접 조회 → `object_type: "chat_completion_stream"`으로 기록됨. **`/v1/responses`도 내부적으로 일반 chat completion 요청으로 변환돼서 다른 클라이언트와 완전히 동일한 `opencode-proxy`(pool) 경로를 탄다** — 프로토콜 자체의 호환성 문제는 아님.
- `pool.log`에서 해당 시각(12:24:45~) 확인 → 요청이 수십 개의 서로 다른 vercel 노드를 순회하며 대부분 `[empty-stream] bytes=0`으로 실패, 그 사이사이 `[model-blacklist] opencode/muse-spark-1.3-contributor-free`와 `opencode/muse-spark-1.2-contributor-free`(동티어 ALT)가 **반복적으로** 찍힘.
- `/health` 확인 결과 그 시점에 50개 vercel 노드 중 30개가 실패 이력, 10개는 실시간 쿨다운 중(일부 쿨다운 최대 30분) — Vercel 레이어의 광범위한 실시간 장애가 동시에 겹쳐있었음(이건 zen 자체 문제 아님 — oracle2 로컬 직결 호출은 2.9초 만에 정상 응답).
- 하지만 **더 심각한 발견**: `[model-blacklist]` 이후 로그 전체를 훑어보니, muse-spark가 **원본으로 직접 서빙된 `[ok]` 기록이 단 한 건도 없고 전부 `ALT=muse-spark-1.2`로만 성공**하고 있었음 — 즉 muse-spark-1.3과 1.2 **둘 다 전역적으로 블랙리스트에 걸려서, 다른 모든 클라이언트(코덱스뿐 아니라)의 요청까지 계속 ALT로만 우회당하는 중**이었음.

## 근본 원인

`pool.js`에는 "이 모델 자체가 zen에서 거부됐다"(`ModelError`, `not supported` 등) 판단되면 그 모델을 `BAD_MODELS`라는 **만료 없는 전역 Set**에 등록해 ALT/카탈로그/프로브에서 영구 제외하는 로직이 있다(2026-08-25 P1 fix):

```js
function isModelError(text) {
  return /ModelError|not supported|does not exist|invalid_request_error|unknown parameter|invalid parameter/i.test(text || '');
}
```

코덱스 CLI가 보내는 `"response_format":{"type":"json_object"}`를 일부 muse-spark 배포가 `400 invalid_request_error`로 거부했는데, 이 정규식이 "파라미터 하나를 거부"와 "모델 자체가 죽음"을 구분하지 못해서 muse-spark-1.3과 그 ALT인 1.2를 **둘 다** 블랙리스트에 올렸다. `BAD_MODELS`가 만료가 없는 Set이라 **pool.js 재시작 전까지 절대 안 풀리고**, 그 이후로 들어오는 모든 클라이언트의 muse-spark 요청이 원본을 시도조차 안 하고 곧장 ALT로 우회됐다(운 나쁘게 ALT마저 Vercel 장애와 겹치면 이번처럼 전체 요청 실패).

## 수정

두 겹 방어:

1. **오판 자체를 차단**: `response_format`/`json_schema` 언급이 있으면 "모델이 죽었다"로 보지 않음 — 그건 이 요청 하나의 파라미터 문제이지 모델 전체 문제가 아님.
2. **혹시 모를 다른 오탐에 대비한 자동 회복**: `BAD_MODELS`를 만료 없는 `Set`에서 **10분 TTL이 있는 맵 기반 객체**로 교체. 기존 `.has()`/`.add()` 인터페이스를 그대로 유지해서 다른 6곳의 호출부는 손대지 않음(diff 최소화).

```js
const BAD_MODEL_TTL_MS = parseInt(process.env.BAD_MODEL_TTL_MS || '600000', 10); // 10min
const BAD_MODELS_EXPIRY = new Map();
const BAD_MODELS = {
  has(id) {
    const exp = BAD_MODELS_EXPIRY.get(id);
    if (exp === undefined) return false;
    if (Date.now() > exp) { BAD_MODELS_EXPIRY.delete(id); return false; }
    return true;
  },
  add(id) { BAD_MODELS_EXPIRY.set(id, Date.now() + BAD_MODEL_TTL_MS); },
};
function isModelError(text) {
  const s = text || '';
  if (/response_format|json_schema/i.test(s)) return false;
  return /ModelError|not supported|does not exist|invalid_request_error|unknown parameter|invalid parameter/i.test(s);
}
```

# P14: `input[N].content did not match any supported type` (재발) — museToInput의 user 배열 콘텐츠 파트 미변환, 전체 함대(38 Vercel + 4 Deno) 배포 (2026-09-10~11 해결)

## 증상

P13 조치 이후에도 코덱스 → `omni1` 콤보 호출이 계속 실패:

```

```

## 원인

`museToInput()`의 `role:'user'` 분기가 `content`가 이미 배열이면(Chat Completions 형식, 예: `[{type:'text', text:'...'}]`) **각 파트 타입을 전혀 변환하지 않고 그대로 통과**시켰다:

```js
} else if (m.role === 'user') {
  const c = Array.isArray(m.content) ? m.content : [{ type: 'input_text', text: ... }];
  input.push({ role: 'user', content: c });   // 배열이면 무변환
}
```

코덱스 CLI가 AGENTS.md 내용을 정확히 이 배열 형태(`role:"user"`, `content:[{type:"text",...}]`)로 주입하는데, Responses API `input` 스키마는 user 파트에 `"text"`가 아니라 `"input_text"`를 요구해서 거부당함. P9는 assistant 쪽(`output_text`)과 top-level `function_call`/`function_call_output`만 고쳤고, **user 쪽 배열 콘텐츠는 그때 테스트 케이스가 전부 평문 문자열이라 놓쳤음**. Vercel/Deno 배포본도 확인해보니 부분적으로만 고쳐져 있었음(문자열 파트만 변환, `{type:'text',...}` 객체 파트는 여전히 무변환) — 오라클2/Vercel/Deno 전부 같은 구멍.

## 수정

`normalizeMuseContentPart()` 헬퍼 추가, `role:'user'`의 배열 content에 `.map()`으로 적용:

```js
function normalizeMuseContentPart(x) {
  if (typeof x === 'string') return { type: 'input_text', text: x };
  if (x && typeof x === 'object') {
    if (x.type === 'text') return { type: 'input_text', text: x.text || '' };
    if (x.type === 'image_url') {
      const url = (x.image_url && x.image_url.url) || x.image_url;
      return { type: 'input_image', image_url: url };
    }
  }
  return x;
}
```

# P15: pool.js가 노드 하나의 라우팅 404로 전체 요청을 즉시 종료 — "요청 스코프 vs 노드 스코프" 오판 (2026-09-11 해결)

## 증상

```
[404]: Route POST /api/index not found
```
코덱스 `omni1` 콤보 호출이 이 404로 즉시 실패, 대화 진행 불가.

## 원인

`pool.js`가 4xx 응답을 받으면 "이 요청 자체가 잘못된 거라 다른 업스트림 재시도가 무의미하다"고 가정하고, 남은 후보를 하나도 시도하지 않은 채 **전체 클라이언트 요청을 즉시 종료**하고 그 4xx를 그대로 돌려준다:

```js
if (upRes.status >= 400 && upRes.status < 500 && upRes.status !== 408 && upRes.status !== 429) {
  res.writeHead(upRes.status, ...);
  return res.end(text);   // 남은 후보 전부 포기
}
```

그런데 `vercel-opencode-proxy-v2` 노드에 직접 테스트해보니 **어떤 요청을 보내도 100% 이 404** — 이건 "요청이 잘못됨"이 아니라 "이 노드 하나의 배포가 깨짐"(아래 P16)이라는, 노드-스코프 문제였다. Kiro 브랜드 게이트웨이(P12)와 같은 패턴: 요청 스코프 vs 노드 스코프를 구분 못 함.

## 수정

플랫폼 레벨 라우팅 404(`"Route ... not found"`)만 좁게 식별해서, 이 경우엔 전체 요청을 죽이지 않고 다음 후보로 넘어가도록 예외 추가:

```js
function isNodeRoutingError(text) {
  return /route\s+\S+\s+\S+\s+not found/i.test(text || '');
}
```

일반 4xx 숏서킷 로직은 그대로 유지(진짜 요청-스코프 문제까지 재시도로 넓히면 P13류 사고 재현), 이 패턴에만 예외 적용.

## 검증

배포 후 실전 요청 5연속 200. `vercel-opencode-proxy-v2`가 여전히 고장난 상태였을 때도(P16 수정 전) 전체 요청은 안 죽고 다음 노드로 넘어가는 것으로 무해화됨.

## 교훈

- **"이 4xx는 재시도해도 소용없다"는 가정은 "모든 업스트림이 같은 코드/설정을 갖고 있을 때만" 성립한다.** 풀처럼 서로 다른 배포본(계정, 리전, 빌드 상태)을 섞어 쓰는 구조에서는, 같은 요청도 노드마다 다른 결과를 낼 수 있다는 걸 항상 전제해야 한다.

```js
if (
```

- **로그에 안 보이는 필드는 "없다"가 아니라 "이 로그가 그걸 안 보여줄 뿐"일 수 있다.** bifrost `logs.db`의 `params` 필드는 `model`/`messages`조차 안 담고 있었다 — 실제 요청의 진짜 근거가 필요하면 그 값을 신뢰하지 말고, 우리가 직접 통제하는 코드(이 경우 `api/index.js`)에 임시 진단 로그를 넣어 실물을 잡는 게 가장 빠르고 확실하다.

# P18: pool.js의 "API 키 감지 시 instance2 직통" 우회 + server.js의 SIGTERM 미처리 90초 정지가 겹쳐 코덱스가 5회 재시도 후 접속 끊김 (2026-09-11 해결)

## 증상

코덱스가 `omni1` 콤보를 계속 호출하면, 특정 시간대에 몰아서 실패하다가 "5회 시도 후 접속이
끊긴다"고 보고됨. bifrost `logs.db` 조회 결과 그 실패들의 타임스탬프가 정확히 그날 진행 중이던
P17 롤아웃 배포 시간대와 겹쳤음 — 그런데 롤아웃이 끝난 뒤에도 산발적으로 재발.

## 원인 ① — `pool.js`가 실키(real API key)를 감지하면 페일오버 전체를 우회한다

```js
// === API Key 감지 시 instance2 로컬 직통 처리 (분산 라우팅 우회) ===
if (hasValidKey) {
  candidates = [{ u: { url: 'http://127.0.0.1:8769', name: 'instance2-direct' }, model: null }];
} else {

```

더미 키(`1`, `sk-dummy`, `sk-proxy-master`)가 아닌 **진짜 API 키**(Kilo JWT, zen `sk-`)가 오면,
50개 노드 페일오버 풀을 통째로 무시하고 **오라클2 로컬 인스턴스(`127.0.0.1:8769`) 단 하나로만**
요청을 보낸다. 대체 후보가 전혀 없어서, 이 인스턴스가 조금이라도 흔들리면 그 요청은 무조건
실패한다. bifrost의 `kilo-gateway`/`opencode-zen1` 프로바이더가 쓰는 키가 전부 이 분기를 타므로,

## 원인 ② — `server.js`가 SIGTERM을 받아도 실제로 안 죽고 90초씩 버틴다

```js
// server.js (수정 전)
http.createServer(...).listen(PORT, HOST, () => console.log(...));
// -> 반환값(서버 인스턴스)을 어디에도 저장 안 함

// api/index.js
process.on('SIGTERM', () => { shuttingDown = true; });  // 새 요청만 503으로 막을 뿐,
                                                          // 서버를 닫거나 프로세스를 끝내지 않음
```

`systemctl restart opencode-proxy`(오늘 P14/P17 배포마다 실행)를 하면, systemd가 SIGTERM을
보내도 프로세스가 안 죽고 `TimeoutStopSec`(기본 90초)까지 버티다가 결국 SIGKILL로 강제종료됨
— journalctl에서 실측 확인:
```
23:12:42 Stopping opencode-proxy.service...
23:14:12 State 'stop-sigterm' timed out. Killing.   ← 정확히 90초
```
**원인 ①(instance2-direct, 대체 후보 없음)과 겹치면서, 오라클2를 재배포할 때마다 약 90초간
Kilo/Zen 키 트래픽 전체가 죽는 창이 생겼다.** 오늘 여러 번 배포했으니 코덱스가 여러 번 이
구간에 걸렸을 것 — "5회 재시도 후 종료"는 재시도할 때마다 매번 같은(죽어있는) 단일 노드만
때렸기 때문에 자연스러운 결과.

## 수정

`server.js`가 서버 인스턴스를 변수에 저장하고, SIGTERM/SIGINT에서 실제로 `server.close()` →
콜백에서 `process.exit(0)`. 10초짜리 안전장치(`setTimeout(...).unref()`)도 추가해서, 혹시
오래 끄는 요청이 있어도 systemd 강제킬보다 먼저 우리가 로그를 남기고 정상 종료한다.

```js
function gracefulShutdown(signal) {
  console.log(`[shutdown] received ${signal}, closing server (in-flight requests get to finish)`);
  server.close(() => { console.log('[shutdown] server closed cleanly, exiting'); process.exit(0); });
  setTimeout(() => process.exit(0), 10000).unref();
}
process.on('SIGTERM', () => gracefulShutdown('SIGTERM'));
process.on('SIGINT', () => gracefulShutdown('SIGINT'));
```

로컬 systemd용(`/opt/opencode-proxy/server.js`, 오라클1/오라클2)과 컨테이너용(`/root/opencode_proxy/server.js` — `/health`/`/ip` 내장, Dockerfile/Northflank/Orkestr/SnapDeploy가 씀) 두 변형 다 반영. git 커밋 `90e9b17`.

## 검증

| 항목 | 수정 전 | 수정 후 |
|---|---|---|
| 오라클2 `systemctl restart` 소요시간 | 1:30.09 (90초, SIGKILL) | 0.029초 |
| 오라클1 `systemctl restart` 소요시간 | 1:30.10 (90초, SIGKILL) | 0.021초 |
| journalctl 종료 로그 | `Killing process ... SIGKILL` / `Failed with result 'timeout'` | `[shutdown] server closed cleanly, exiting` → `Deactivated successfully` |

## 교훈

- **"재시작했다"와 "재시작이 빠르고 안전하게 끝났다"는 다르다.** `systemctl restart`가 성공
  종료 코드를 반환해도(결국 active가 되긴 하니까), 그 안에서 90초간 강제종료를 기다린
  구간이 있었다는 건 별도로 확인해야 한다 — `time systemctl restart ...`와 journalctl의
  `Killing process`/`timeout` 여부로.
- **"신호를 받아서 플래그를 세팅한다"와 "실제로 서버를 닫고 프로세스를 끝낸다"는 다른 일이다.**
  `shuttingDown=true`만으로는 아무것도 안 끝난다 — `server.close()` + `process.exit()`가
  반드시 있어야 하고, 그러려면 애초에 서버 인스턴스에 대한 참조를 어딘가에 들고 있어야 한다.
- **단일 장애점(원인 ①) 위에서 반복적으로 배포/재시작(원인 ②)을 하면, 두 문제가 서로를
  증폭시킨다.** 각각은 독립적으로 봐도 문제지만, 겹쳤을 때 실제 사용자 체감 장애가 발생했다
  — 근본 원인을 찾을 땐 "가장 최근에 건드린 것"과 "원래 있던 설계"를 같이 의심할 것.

# P19: `instance2-direct` 단일 장애점 제거 — 키 있는 요청도 정상 페일오버 태우기 (2026-09-11 해결)

## 배경

P18에서 발견한 `pool.js`의 "API 키 감지 시 instance2 로컬 직통" 설계 — 더미 키가 아닌 실키(Kilo JWT, zen `sk-`)가 오면 50개 노드 페일오버를 통째로 건너뛰고 오라클2 로컬 인스턴스 하나에만(대체 후보 없음) 요청을 보내던 로직. P17/P18 수정 이후에도 코덱스가 간헐적으로 계속 실패해서 재확인한 결과, 이 단일 노드가 잠깐 타임아웃되거나(`This operation was aborted`) zen/kilo 자체 레이트리밋(`429`)에 걸리면 — 원래 50개 노드 풀이었으면 다음 노드로 넘어갔을 상황인데 — 대체 후보가 없어 그대로 실패하고 있었다.

## 결정

이 설계 자체를 폐기: **키가 있든 없든 전부 `buildAttemptPlan`(정상 페일오버)을 타도록 변경.** 단, 실키로 온 요청은 반드시 그 실키를 그대로 업스트림에 실어 보내야 한다 — 무료(익명) 사용량과 키 사용량을 분리해서 **최종 가용 사용량 자체를 늘리는 게** 이 시스템의 목적이기 때문(익명 quota만 쓰면 그 계정의 실키 quota는 그냥 낭비됨).

## 수정

```js
// 변경 전: 실키 감지 시 후보 1개 고정
if (hasValidKey) {
  candidates = [{ u: { url: 'http://127.0.0.1:8769', name: 'instance2-direct' }, model: null }];
} else {
  candidates = buildAttemptPlan(requestedModel);
}

// 변경 후: 항상 정상 페일오버
const candidates = buildAttemptPlan(requestedModel);
```

키 자체는 별도 처리 없이도 그대로 전달된다 — `attempt(u, req, rawBody)`가 `host`/`connection`/`content-length`/`accept-encoding`만 빼고 클라이언트 헤더(`Authorization` 포함)를 이미 있는 그대로 업스트림에 복사하고 있었기 때문(§2에서 이미 검증된 사실). 즉 이번 수정은 "우회 로직 삭제" 그 자체가 전부이고, 키 전달 로직은 손댈 필요가 없었다.

## 검증

실제 Kilo JWT 키로 4회 연속 요청 → 4개의 **서로 다른** 노드(`vercel-opencode-proxy-v3-*` 2개, 오라클1 직결, `opencode-proxy` 별칭)로 분산 성공. 실제 zen `sk-` 키로도 3회 연속 → 2개의 다른 Vercel 노드로 분산 성공. 둘 다 실키가 각 업스트림에 정상 전달돼 처리됐음(각 노드의 `isKiloKey`/`isOpenCodeZenKey` 가드도 그대로 통과).

## 교훈

- **"우회/직통 경로"는 언뜻 최적화처럼 보여도, 그 경로에 페일오버가 없으면 시스템 전체의 안정성을 그 경로의 단일 노드 가용성으로 깎아내린다.** 왜 그 우회가 있었는지 먼저 물어봤던 게(P18에서) 옳았고, 확인 결과 "키별 상태를 인스턴스 로컬에 고정하기 위함"이 아니라 그냥 예전에 편의상 넣어둔 것으로 보임 — 헤더 전달은 이미 범용적으로 잘 되고 있었으니 굳이 우회가 필요 없었다.
- **키 트래픽을 페일오버 풀에 태울 때는 "익명 사용량과 키 사용량을 분리해서 최종 가용량을 늘린다"는 목적을 놓치지 않아야 한다.** 그냥 하드코딩된 더미 키로 바꿔버리면 편해 보이지만, 실제로는 사용자의 유료/한도 있는 키 자원을 못 쓰는 셈이 된다.

**1. `normalizeMuseContentPart(x, role)` role-aware화** — `유의사항.md` §정규식 이중 이스케이프 금지·§MUSE_EFFORT 6키 유지:

```js
  const targetRole = role === 'assistant' ? 'assistant' : 'user';
  if (typeof x === 'string') return { type: targetRole==='assistant'?'output_text':'input_text', text: x };
  if (x.type === 'text') return { type: targetRole==='assistant'?'output_text':'input_text', text: x.text||'' };
  if (x.type === 'input_text' || x.type === 'output_text' || x.type === 'refusal') return x;

}
```

## 증상

`POST /v1/messages` (Anthropic API)가 Hermes/Claude Code에서 tool/image를 쓰면 **200이지만 기능이 빠지는 침묵 실패**. 로그상 에러 없이 `finish_reason`만 `end_turn`으로 끝나고 `tool_calls` 0개.

## 원인

원래 `/opt/opencode-proxy/server.js:575`( `02_프록시_아키텍처_API.md:85` )는 `anthropicToOpenAI` → `forwardToUpstream` → `openAIToAnthropic` 3단계로 `system`/`content`(`tool_use`/`tool_result`/`image`)/`tools`(`input_schema→parameters`)/`tool_choice`(`auto/any/tool→required/function`)를 모두 변환했으나, 현재 `api/index.js:870-945`는 단순 패스스루로 단순화됨:

```js
let openReq = { model: upstreamModel, messages: body.messages||[], ... stop: body.stop_sequences };
// body.system, body.tools, body.tool_choice, image/tool_result 매핑 전부 누락
```

* `system: "string"`/`[{type:"text"}]` → `messages`에 합치지 않아 시스템 프롬프트 소실
* `content: [{type:"image", source:{type:"base64"}}]` → OpenAI는 `{type:"image_url", image_url:{url:"data:..."}}`만 허용 → 400 또는 무시
* `content: [{type:"tool_result"}]` → OpenAI는 `role:"tool"` + `tool_call_id` 별도 메시지 필요 → 그대로 전달 시 upstream이 tool 결과를 못 찾아 루프 붕괴
* `tools: [{name,input_schema}]` → OpenAI는 `{type:"function", function:{parameters}}` 필요, `tool_choice: {type:"any"}` → `"required"` 미변환 → upstream이 tool 정의 자체를 못 받아 `tool_calls` 0개

`skill.md` §4가 `museToInput`만 강조한 탓에 `messages`는 "비스트리밍만 완전 변환"(`09_...md:88`)으로 방치, pool 로그에서도 `POST /v1/messages` 자체가 거의 안 찍혀 장애가 가려짐.

## 수정

`api/index.js`·`vercel/api/index.js`·`deno/main.ts` 3곳 동기화 (`/root/opencode_proxy@8078f6c`):

* `anthropicSystemToMessages(system)` — top-level `system` 문자열/배열 → `[{role:"system", content}]`
* `anthropicContentToOpenAIBlocks(content)` — `tool_result`는 별도 `tool` 메시지로 분리, `image` base64→`data:` URL/`image_url`로 변환, `text` 유지
* `anthropicMessagesToOpenAI(body)` — `system` + `messages` 전체 순회: `user`의 `tool_result` 분리, `assistant`의 `tool_use` → `tool_calls`, `system` in messages 허용
* `anthropicToolsToOpenAI(tools)` — `input_schema`→`parameters`, 이미 OpenAI 형식이면 passthrough
* `anthropicToolChoiceToOpenAI(tc)` — `auto→auto`, `any→required`, `tool{name}→{type:"function"}`

`/v1/messages` 핸들러 `api/index.js:994`를

```js
const anthMessages = anthropicMessagesToOpenAI(body);
const anthTools = anthropicToolsToOpenAI(body.tools);
const anthToolChoice = anthropicToolChoiceToOpenAI(body.tool_choice);
let openReq = { model: upstreamModel, messages: anthMessages, ..., ...(anthTools?{tools:anthTools}:{}), ...(anthToolChoice?{tool_choice:anthToolChoice}:{}) };
```

로 교체 — `museViaResponses` 경로(`museToInput`)와 `forward('/chat/completions')` 경로 모두 이 변환된 `openReq`를 사용하므로 `muse`·`non-muse`·`kilo` 전부 커버. `유의사항.md` §muse 경로별 variant·§정규식 규칙 유지.

`11_res_chat_mes_passthrough_및_cliproxyapi_연동.md` §"남은 이슈" 2번에서 이미 발견은 되어 있었지만("CLIProxyAPI가 `/responses` 요청에 기본 tool(`image_generation`)을 자동 주입하는 것으로 보이고 zen이 이를 거부한다") 원인 확정과 수정은 미뤄져 있었다.

## 원인

zen 업스트림에 `tools:[{type:"image_generation"}]`을 직접 실어 보내 재현 확인 — zen은 이 tool 타입 자체를 지원하지 않아 무조건 400을 낸다. 반면 클라이언트가 CLIProxyAPI로 보낸 원 요청의 `tools`에는 이 항목이 없다. 즉 **CLIProxyAPI의 codex 실행기가 `/responses` 요청을 만들 때 `tools`에 `{type:"image_generation"}`을 기본값으로 자동 주입**하고, 그걸 우리 `/res/v1/responses`가 그대로(순수 passthrough 설계, §11) zen에 전달하면서 항상 실패했다.

CLIProxyAPI 쪽 `payload.filter`(gjson/sjson path 기반 필드 제거) 옵션으로 설정만으로 막을 수 있는지 조사(`config.example.yaml`, `help.router-for.me/configuration/options`) — `filter`는 특정 JSON path를 제거하는 규칙은 있지만, "조건에 맞는 배열 요소만 제거"(`tools.#(type=="image_generation")` 같은 gjson 쿼리)에 대한 공식 예시나 지원 보장이 없어, config 패치보다 opencode-proxy 쪽에서 직접 필터링하는 쪽을 택함.

## 수정

`/res/v1/responses` 순수 passthrough 라우트(`api/index.js`/`vercel/api/index.js`/`deno/main.ts` 3곳 동일 적용)에서, 이미 모델 검증 때문에 파싱해둔 바디의 `tools` 배열에 `type === 'image_generation'` 항목이 섞여 있을 때만 그것만 제거하고 재직렬화해서 전달한다. 그 tool이 없는 통상 케이스는 `rawBody`를 그대로(바이트 단위 동일) 전달해 "바디 무변형" passthrough 원칙을 최대한 유지한다.

```js
let outBody = rawBody;
if (pathname === '/res/v1/responses' && Array.isArray(body.tools) && body.tools.some(t => t && t.type === 'image_generation')) {
  const filtered = body.tools.filter(t => !(t && t.type === 'image_generation'));
  const patched = { ...body, tools: filtered };
  if (!filtered.length) delete patched.tools;
  outBody = JSON.stringify(patched);
}
```

3개 사본 수정 → 오라클2 `bash redeploy.sh all` 실행(`redeploy.sh`는 S3 마운트 위에 있어 실행비트가 안 먹으므로 `bash`로 직접 실행) → Vercel 38 + Deno 4 + local(oracle1/오라클2) 2, **44/44 OK** → v3/v4는 재배포마다 URL이 바뀌므로 새 URL 20개로 `opencode-pool`의 `POOL_UPSTREAMS`(47개) 갱신 후 `daemon-reload && restart opencode-pool`.

## 교훈

- **중간 게이트웨이(CLIProxyAPI 등)가 요청에 클라이언트도 모르는 기본값을 몰래 주입하면, 업스트림이 그 필드 하나 때문에 요청 전체를 거부해도 증상은 "우리 프록시 버그"처럼 보인다.** 원인 확정은 항상 "그 필드를 뺀 동일 페이로드"와 "그 필드만 넣은 동일 페이로드"를 업스트림에 직접 쏴서 대조하는 걸로.
- **"바디 절대 안 건드린다"는 passthrough 설계 원칙은 기본으로 지키되, 특정 필드가 100% 확정적으로 업스트림에서 거부된다는 게 실측으로 확인되면, 그 필드 하나만 제거하는 예외는 원칙 훼손이 아니라 "passthrough가 항상 실패하는 상황을 막는" 최소 개입으로 취급한다** — 조건 없이 전체 변환 로직을 다시 들이는 것과는 다르다.

# P25: `/res|chat|mes/v1/models`가 유료 모델까지 노출 — 무료 필터 누락 (2026-09-11 해결)

POST 쪽은 애초에 요청 바디를 안 건드리는 게 맞는 설계지만, GET `/models`는 이 프로젝트 전체의 "무료 모델만 노출" 기조(레거시 `getFreeModelsExpanded()`가 키 종류와 무관하게 항상 강제)와 어긋나는 예외가 됐다 — 설계 전환 당시 GET `/models`를 POST와 동일한 원칙으로 한데 묶어 처리한 게 누락 원인.

## 수정

`/res|chat|mes/v1/models` 핸들러에서 zen 응답을 파싱한 뒤 `data` 배열만 `id.endsWith('-free') || KNOWN_FREE_EXTRA.has(id)` 기준(레거시 `getFreeModelsExpanded()`와 동일 기준)으로 필터링해서 반환한다. `id`는 `opencode/` 접두사 없이 zen 네이티브 그대로 유지(CLIProxyAPI 등이 그대로 참조하는 형식과 일치시키기 위해 — 경로 자체가 이미 프로바이더를 명시).

```js
const upstreamJson = await fr.json();
const filtered = Array.isArray(upstreamJson.data)
  ? upstreamJson.data.filter(m => m && m.id && (m.id.endsWith('-free') || KNOWN_FREE_EXTRA.has(m.id)))
  : [];
```

`api/index.js`/`vercel/api/index.js`/`deno/main.ts` 3곳 동일 적용.

## 교훈

- **"바디를 안 건드린다"는 passthrough 원칙은 요청 본문(POST)에 대한 것이지, GET 리스트 응답에도 무조건 같은 원칙을 적용해야 하는 건 아니다.** 여러 엔드포인트를 한 세트로 묶어 설계할 때, 각 엔드포인트가 실제로 지켜야 할 불변조건(이 경우 "무료만 노출")이 다를 수 있다는 걸 놓치기 쉽다.

# P26: `/res|chat|mes/v1/*`는 zen 전용이라 Kilo 키가 무시됨 — 오해 해소 및 `/kilo/v1/*` 전용 라우트 신설 (2026-09-11)

"Kilo API 키를 넣으면 Kilo 모델만, Zen 키를 넣으면 Zen 모델만 반환되도록 되어 있나?"라는 질문에서 출발. 레거시 `GET /v1/models`(+ `/v1/chat/completions`)는 실제로 그렇게 분기돼 있음을 실측으로 확인(Kilo 키 → Kilo 무료 22개, Zen 키 → Zen 무료 8개, 키 없음 → 결합)했지만, 신규 `/res|chat|mes/v1/models`(+ POST 쪽)는 Kilo 키를 넣어도 넣지 않아도 **항상 zen 무료 모델만** 반환됐다.

## 원인 (버그 아님, 설계)

`/res|chat|mes/*`는 2026-09-11 설계 전환(`11_res_chat_mes_passthrough_및_cliproxyapi_연동.md`) 당시부터 **zen 전용**으로 만들어졌다 — POST 핸들러(`NATIVE_PASSTHROUGH_ROUTES`)도 항상 `UPSTREAM`(zen)으로만 forward하고 Kilo 분기가 아예 없다. ## 교훈

`openai-compatible-chat-d0b2f3d7-5428-496c-ab0a-f30181df289a`)로, `base_url:
"http://omniroute-scsi:8317/v1"` — 즉 CLIProxyAPI 자신을 가리킨다. `/opt/opencode-pool/pool.log`에서
같은 시각 `/chat/v1/chat/completions`로 muse-spark 요청이 실제로 들어온 걸 확인했고, CLIProxyAPI

## 배포/재시작 사고 — 프로세스가 자동으로 재시작되지 않음

기존 문서(`11_...md` §4)는 "재시작 필요"라고만 적혀 있었는데, 이번에 실제로 `sh -c 'kill <pid>'`로
CLIProxyAPI를 종료시켰더니 **부모 프로세스(omniroute 메인, PID 20)가 자동으로 재기동해주지 않았다** —
`/proc` 스캔으로 재확인한 결과 프로세스가 완전히 죽은 채로 남아있어 잠깐 동안(~10초) `:8317` 전체가
다운됐다. `kubectl exec pod -- kill <pid>`(래핑 없이)는 컨테이너에 `kill` 바이너리 자체가 없어서 먼저
실패했고(`exec: "kill": executable file not found`), `sh -c 'kill <pid>'`로 감싸야 셸 내장 `kill`이 동작.
자동 재기동이 없다는 걸 뒤늦게 알아서, `sh -c 'nohup /app/data/bin/cliproxyapi --config
/app/data/services/cliproxy/config.yaml > /tmp/....log 2>&1 &'`로 직접 백그라운드 기동해서 복구.
`disown`은 이 컨테이너 셸에 없어서 생략(문제 없음 — `kubectl exec` 세션 종료와 별개로 nohup만으로
프로세스가 살아남는 것을 확인).

- `POST /v1/chat/completions` `model:"opencode-zen/muse-spark-1.3-contributor-free"`(마스터 키) →
  이전엔 30초+ hang, 수정 후 즉시 `400 {"code":"model_not_found", "message":"unknown provider for
  model opencode-zen/muse-spark-1.3-contributor-free"}` — 빠르게 실패하므로 최소한 무한 대기는 사라짐
- `POST /v1/responses` `model:"zen/muse-spark-1.3-contributor-free"` → 여전히 `200 completed` 정상

## 교훈

- **같은 모델을 두 개의 다른 프로토콜 섹션(`openai-compatibility` vs `codex-api-key`)에 동시에 등록해두면,
  라우팅 계층(OmniRoute의 모델-프로바이더 매칭 등)이 어느 쪽으로 보낼지는 그쪽 로직에 달려있다 —
  "한쪽은 되니까 안전하다"가 아니라 잘못된 쪽 경로가 실제로 트래픽을 받을 수 있다는 걸 항상 가정할 것.**
  이번처럼 사용자에게 낯선 provider 이름(`mycli`)이 로그에 나오면, 그게 우리가 등록한 provider 이름과
  다르더라도 결국 같은 CLIProxyAPI 인스턴스로 들어와서 같은 config.yaml 매칭 로직을 타는지부터 확인.
- **"재시작하면 된다"고 문서에 적혀 있어도, 그 프로세스가 죽었을 때 자동으로 살아나는지(supervisor 유무)는
  실제로 죽여보기 전엔 모른다.** 이번에 kill 후 자동 재기동이 없다는 걸 실전에서 알게 됐다 — 프로덕션
  프로세스를 재시작할 때는 "죽이면 끝"이 아니라 "죽인 뒤 실제로 살아있는지"까지 반드시 확인 스텝에 포함.
- `kubectl exec pod -- <cmd>`는 최소 컨테이너 환경에서 셸 내장 명령(`kill` 등)이 필요하면 반드시
  `sh -c '<cmd>'`로 감싸야 한다 — 감싸지 않으면 PATH에 실제 바이너리가 없어 즉시 실패한다(이 컨테이너엔
  `ps`/`curl`도 없다는 게 이미 알려진 제약 — `kill`도 마찬가지였다).
